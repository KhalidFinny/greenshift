## HIGH: Hard Gate

### F-24 Autosave never persists while Lokasi and Sektor are empty, and says nothing

`packages/business/src/lib/use-business-draft.ts:114-123` (the `catch` that
comments away a real failure)
`packages/business/src/dashboard.tsx:399-441` (the autosave effect sending `""`)
`apps/api/src/modules/business/drafts/drafts.service.ts:62-68`
`apps/api/src/modules/business/business.validation.ts:71-76`

The wizard's initial state is `lokasi = ""` and `sektor = ""`. The autosave
effect sends every key on every keystroke, including those empty strings. The
server's per-step rules read a *present* key as a value:

```
lokasi: ""  -> 400 {"fields":{"lokasi":"Lokasi wajib diisi."}}
sektor: ""  -> 400 {"fields":{"sektor":"Pilih sektor."}}
both filled -> 200
nulls instead of "" -> 200
```

Measured end to end in the browser:

| Step | Result |
|---|---|
| Fresh draft, type a project name + a number, wait past the 800 ms debounce | `PUT /drafts/:id` **400**, repeated per keystroke batch |
| `GET /drafts/:id` after that | **404**: nothing was stored |
| Reload the page | every field empty; the work is gone |
| Same form with a complete step 1 seeded | resume works, fields come back |

So the draft API, the debounce and the resume path all work; the wizard simply
never sends a savable body until Lokasi and Sektor are both filled. A user who
names the project, fills the numbers, and then closes the tab loses all of it,
with no error: `saveDraft` is `silent: true` in the client and the hook's `catch`
only carries a comment.

Rules **R-26** (a form that cannot submit), **C-2**, **R-27** (an error state
that is never shown), and the antislop-code entries "Error Handling Theater" and
"Stubs Shipped as Code" (a failure path that looks handled and is not).

Direction: send `null` for an untouched field rather than `""` (one `|| null` per
key at the call site), or treat `""` as absent server-side. Either way the
failure has to become visible: a "not saved" state next to the save, not a
comment.

### F-25 The rejected autosaves also burn the mutation budget, and the 429 is silent

`apps/api/src/lib/mutation-limit.ts:19-36` (30 per 600 s, per IP and per user)
`apps/api/src/modules/business/drafts/drafts.routes.ts:20-58`

The rate-limit middleware runs **before** the handler, so every F-24 rejection
still consumes one of the 30 allowed draft mutations per 10 minutes. Continuing
to type during F-24 therefore walks the user toward the wall; once reached, all
saves return

```
429 {"error":{"code":"RATE_LIMITED","message":"Too many attempts, please try again later"}}
```

which is the same silent path as F-24 (`silent: true`). Measured: this session
exhausted the bucket for `business1` inside ~20 minutes of ordinary form
interaction, and the wizard kept accepting input while saving nothing.

A 30-per-10-minutes bucket suits discrete mutations; a debounced autosave is not
one.

Rule **R-27** (a failure the user cannot see), plus the antislop-code
"Error Handling Theater" entry.

Direction: give autosave its own bucket sized for typing (or count only
*successful* mutations), and surface a persistent "draft not saved" indicator
until a save succeeds.

### F-27 Business wizard focus indicators are 30 % opacity rings

`packages/business/src/dashboard.tsx:597,716,753` (and `:1005,1041`)

These three controls are `outline-none` with

```
focus-visible:ring-2 focus-visible:ring-ring/30
```

and no `focus-visible:border-ring` to fall back on, unlike every button and input
in `@greenshift/ui`. `--ring` is `#07815F` (confirmed at runtime). Composited at

the "Coba lagi" retry link. The other two (`:1005`, `:1041`) also use `/30` but
pair it with `focus-visible:border-ring`, so the full-opacity border (4.64 : 1)

## Not verified, and why

Stated as gaps, not as passes.

1. **Wizard steps 2, 3 and 4 were never rendered in the browser.** Reaching step
   2 needs a valid step 1, and F-24/F-25 blocked both routes to it (autosave
   cannot store the lokasi/sektor state, and the draft bucket was exhausted). The
   three views were audited by reading, and every string in them is in the F-28
   inventory, but their runtime layout, states and upload flow are unproven.
   Re-check immediately after the F-24 fix, and again after translation.
2. **File upload was not exercised.** `POST /drafts/:id/documents` was proven by
   the previous session over HTTP, not through the wizard's own controls.
3. **Full Tab traversal was not walked**, for the reason audit 002 recorded: this
   harness drops synthetic keyboard input, so `:focus-visible` styles cannot be
   triggered by `page.keyboard`. F-27 is therefore computed from the class and
   the `--ring` value rather than photographed.
4. **Eight vendor routes and two broker detail routes were not measured at
   390 px**: `/vendor/tenders`, `/vendor/settings`, `/vendor/notifications`,
   `/vendor/performance`, `/vendor/portfolio-performance`, `/vendor/projects`,
   `/vendor/active-projects`, `/vendor/project-detail`, `/vendor/tender-detail`,
   `/broker/project-detail`, `/broker/report-detail`. Their static classes were
   swept; only the runtime geometry is missing.
5. **The upload slots in step 1** accept three documents whose remove buttons are
   `size="icon-sm"` (F-29); whether the remove path is keyboard-reachable was not
   exercised.
